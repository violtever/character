# Security Specification — xocyberluv's character archive

## Data Invariants
1. **Public Read / Admin Write Archive**: `/characters`, `/categories`, and `/gallery` are readable by Guests, Users, and Admins. Only verified Admins (`request.auth.token.email_verified == true` and bootstrapped admin email or `/admins/{uid}`) may create, update, or delete records.
2. **Strict Role Immutability**: Standard users registering via `/users/{uid}` MUST only create documents with `role == 'user'`. Regular users can NEVER modify their `role` field or write to `/admins/{uid}`.
3. **PII Isolation**: `/users/{uid}` contains `email` and is strictly readable only by the owner (`isOwner(uid)`) or a verified Admin (`isAdmin()`). `/usernames/{username}` and `/publicProfiles/{uid}` contain zero PII.
4. **Personal Favorites Integrity**: `/users/{uid}/favorites/{characterId}` is accessible only by the verified owner (`isOwner(uid)`), requires `userId == request.auth.uid`, and verifies that `/characters/{characterId}` exists before creation.
5. **Temporal & Structural Integrity**: All `createdAt` / `updatedAt` timestamps must equal `request.time`; `createdAt`, `uid`, and `createdBy` are immutable on update; every string and array field is bounded in size; all document keys are strictly allowlisted with `hasOnly`.
6. **Music Library & Audio Storage Integrity**: `/tracks/{trackId}` and `/tracks/{trackId}/audioChunks/{chunkId}` are publicly readable so Guests and Users can listen to archive music, while creating, editing, replacing audio, and deleting are strictly restricted to verified Admins (`isAdmin()`). Audio chunks are immutable (`allow update: if false`), bounded to `<= 600,000` chars per chunk and `<= 40` chunks, require `exists(/tracks/{trackId})`, and enforce `resource.data.trackId == trackId` on `list`.
7. **Forum Authorization, Restriction Gate & Anti-Spoofing**: `/forumPosts/{postId}`, `/forumComments/{commentId}`, and `/forumLikes/{likeId}` are publicly readable by Guests/Users/Admins. Only verified authenticated accounts NOT currently restricted or suspended in `/userRestrictions/{uid}` (verified server-side against `request.time.toMillis()`) may create posts or comments. Regular Users can NEVER set `authorRole: 'admin'`, `isPinned: true`, `pinnedAt > 0`, `pinOrder > 0`, `isFeatured: true`, `isImportant: true`, or `importantAnnouncedAt > 0` on create or update — those privileges are strictly enforced by `isAdmin()` in Firestore rules.
8. **Profile Immutability & PII Split**: Users editing `/users/{uid}` and `/publicProfiles/{uid}` may ONLY mutate `displayName`, `photoURL`, and `updatedAt`. `username`, `email`, `uid`, and `role` are strictly immutable for non-Admin owners. `/publicProfiles/{uid}` contains zero PII (no `email`).
9. **Forum Rules Versioning & Acceptance**: `/forumRulesConfig/current` is publicly readable and writable only by `isAdmin()`. `/forumRulesAcceptances/{userId}` is readable/writable only by `isOwner(userId)` or `isAdmin()`, storing the accepted rules version and server timestamp.
10. **Moderation, Restrictions & Anti-Tampering**:
    - `/forumViolations/{violationId}` is readable only by the owning user (`userId == request.auth.uid`) or `isAdmin()`. Users may create a violation record only for themselves with `status == 'unread'` and `appealStatus == 'none'`, and may update ONLY their own un-appealed record to submit an appeal (`appealRequested: true`, `appealStatus: 'pending'`, `appealReason`, `updatedAt`). Users can NEVER dismiss their own warnings or clear strikes.
    - `/userRestrictions/{userId}` is readable only by `isOwner(userId)` or `isAdmin()`. Non-admin owners can NEVER decrease `warningCount` or shorten `postRestrictedUntil`, `commentRestrictedUntil`, or `suspendedUntil`. Only `isAdmin()` may lift restrictions, dismiss strikes, or impose/adjust penalties.
    - `/adminAuditLogs/{logId}` is append-only (`allow update, delete: if false`) and readable/creatable exclusively by `isAdmin()`.
11. **Strict Notification Privacy & Important Announcements**:
    - `/notifications/{notificationId}` is strictly private per recipient: `allow get` requires `recipientId == request.auth.uid || isAdmin()`, and `allow list` strictly enforces `resource.data.recipientId == request.auth.uid` so no user can EVER read another user's private notifications.
    - Regular users may only create `interaction` notifications for OTHER users (`actorId == request.auth.uid && recipientId != request.auth.uid`) referencing an existing post, their own `warning` notification, or an admin escalation alert targeting a verified admin profile (`publicProfiles/{recipientId}.role == 'admin'`). Only `isAdmin()` may create `important_post` or arbitrary `system` notifications.
    - `/importantAnnouncements/{postId}` is publicly readable (non-PII excerpt of Admin important pinned posts) and writable exclusively by `isAdmin()`.

## Dirty Dozen Adversarial Payloads (Must Return PERMISSION_DENIED)
1. **Restricted User Bypass**: A user with `postRestrictedUntil > request.time.toMillis()` in `/userRestrictions/{uid}` attempting to `create /forumPosts/POST-BYPASS` directly → Denied by `isPostRestrictedNow()`.
2. **Self-Unban / Strike Reset Attack**: A restricted user attempting to `update /userRestrictions/{uid}` lowering `warningCount` or setting `postRestrictedUntil: 0` → Denied by monotonic non-decreasing check.
3. **Self-Dismiss Violation Attack**: A user attempting to `update /forumViolations/{id}` setting `status: 'dismissed'` or `appealStatus: 'approved'` → Denied by owner `affectedKeys().hasOnly(['appealRequested', 'appealReason', 'appealStatus', 'updatedAt'])` and `appealStatus == 'pending'`.
4. **Cross-User Private Notification Snooping**: User A attempting `get` or `list` on `/notifications` where `recipientId == userB` → Denied by `resource.data.recipientId == request.auth.uid`.
5. **Fake Important Announcement Spoofing**: Regular user attempting to create `/importantAnnouncements/POST-1` or `/notifications/N-1` with `type: 'important_post'` → Denied by `isAdmin()`.
6. **Self-Interaction Notification Spam**: Regular user creating `/notifications/N-2` with `type: 'interaction'` and `recipientId == request.auth.uid` → Denied by `recipientId != request.auth.uid`.
7. **User Admin Role or Important-Pin Spoofing**: Regular user creating `/forumPosts/POST-2` with `{ authorRole: "admin", isImportant: true }` → Denied by `isAdmin()`.
8. **Email Spoofing Admin**: Unverified token (`email_verified: false`) matching admin email attempting to edit `/forumRulesConfig/current`, dismiss violations, or write `/adminAuditLogs/LOG-1` → Denied by `isVerified()`.
9. **Audit Log Tampering**: Even an Admin attempting to `update` or `delete` an existing `/adminAuditLogs/{logId}` entry → Denied by `allow update, delete: if false`.
10. **Shadow Field Injection**: Any user creating `/forumViolations/V-1` or `/notifications/N-3` with undeclared ghost field `forceBypass: true` → Denied by `hasOnly`.
11. **Timestamp Forgery**: Creating `/forumRulesAcceptances/{uid}` or `/forumViolations/V-2` with client-forged `createdAt`/`acceptedAt` != `request.time` → Denied.
12. **ID Poisoning & Oversized Payload**: Submitting >3,000-char violation text, >500-char notification body, or path traversal document IDs → Denied by `isValidId` and validation helpers.
